AI 智能出行助手 · 产品方案摘要

一份面向 AI PM 面试的作品集配套页 · 从「用户问题」出发，而非「技术清单」

一句话定位：用户只描述出行需求，由 Agent 自动理解意图、选择工具、组合结果并给出完整方案——把跨「天气 / 地图 / 高铁」的信息拼接与决策从用户身上转移给系统。

1. 用户问题

跨城市出行时，用户往往需要连续完成「查天气 → 查目的地 → 查路线 → 查高铁 → 再调整计划」。传统工具的问题不是「没有功能」，而是信息分散在多个工具中，用户要自己完成信息拼接和决策。痛点是信息分散 + 自行拼接，而非「缺少某个功能」。

目标用户：高频跨城通勤者、商务出差党、自由行游客——需要「一句话把天气 + 路线 + 车次一次问完」。

2. 为什么是 Agent，而不是固定 Workflow

出行需求具有较强不确定性：用户可能只问天气，也可能同时问天气 + 路线 + 高铁，还可能在多轮中临时改变目的地。相比「固定流程 + 分支判断」的 Workflow，Agent 更适合根据用户意图动态决定调用哪些工具、以什么顺序调用。这不是「技术很酷所以用了 Agent」，而是产品需求形态决定了技术形态——把天气、地图、高铁封装成可插拔 MCP 工具，让 LLM 中枢负责编排。

4. 核心用户流程

用户输入
「明天东莞天气？东莞到深圳怎么走」→ Agent 理解意图→ 拆解需求
天气 / 出发地 / 目的地 / 路线→ 调用工具
天气 + 地图 + 高铁 MCP→ 结果融合→ 完整出行建议

5. MVP 范围

P0（已交付）：天气 / 路线 / 多工具协同 / 多轮 / 模糊需求澄清。
P1（已交付）：高铁线路参考 / POI 容错 / 海外城市。
P2（V2 体验）：流式输出 / 历史会话增强。

7. 产品边界（可信 AI 的基本盘）

高铁为「线路参考，以 12306 为准」；跨国出行提示乘飞机（暂不接航班工具）；地图依赖高德 API（缺省优雅降级）；天气默认 Open-Meteo（免费免 Key）。边界在一开始就写进产品定义，而不是 Demo 跑出来再补。

两项目组合 = 「知识型 AI（RAG）+ 行动型 AI（Agent）」，恰好覆盖最典型的 AI 应用形态。即使 Demo 是出行 / 知识库场景，这套方法论可直接迁移到招聘方的业务系统。
